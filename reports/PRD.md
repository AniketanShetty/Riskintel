# RiskIntel Product Requirements Document (PRD)

**Role:** Principal Product Architect  
**Status:** FROZEN FOR IMPLEMENTATION  
**Version:** V1.0

---

## 1. Business Problem
Traditional loan underwriting processes are a black box for applicants and highly manual for bank employees. Applicants often receive generic rejections without actionable feedback, leading to poor customer experience and brand erosion. Conversely, loan officers waste significant operational hours manually verifying eligibility criteria for applicants who do not mathematically qualify. Furthermore, applying opaque machine learning models to credit decisions exposes institutions to severe regulatory risk under the Fair Credit Reporting Act (FCRA) and Equal Credit Opportunity Act (ECOA). 

RiskIntel solves this by bifurcating the process into an instantaneously explainable deterministic rule engine for gating, followed by a scientifically validated machine learning profiling engine for strategic credit assessment.

## 2. Target Users

**Primary User: Loan Applicants (B2C)**
*   Individuals seeking personal or business credit.
*   Needs: Transparency, immediate feedback, and actionable guidance on how to improve their financial health if rejected.

**Secondary User: Bank Employees / Underwriters (B2B)**
*   Credit analysts and loan officers.
*   Needs: Reduced manual screening time, automated risk tiering, and mathematically backed borrower archetypes to accelerate final manual approvals.

**Tertiary User: Compliance Officers (Internal)**
*   Needs: Immutable audit trails and perfect mathematical explainability for every adverse action.

## 3. Product Goals
*   **Transparency:** Provide applicants with precise, actionable intelligence rather than generic "approved/rejected" notices.
*   **Efficiency:** Automate 100% of top-of-funnel eligibility filtering to zero out manual review time for fundamentally unqualified applicants.
*   **Compliance:** Guarantee that 100% of adverse actions (rejections) are generated by mathematically deterministic, fully logged rules.
*   **Intelligence:** Leverage scientifically validated ML clustering to group approved borrowers into strategic archetypes, optimizing credit limit allocations.

## 4. Success Metrics
*   **Auto-Decision Rate:** >85% of applicants receive an instant terminal decision or automated tiering without manual intervention.
*   **Latency:** p95 API response time < 500ms for the full Orchestrator DAG.
*   **Underwriter Time Saved:** 40% reduction in time-to-decision for applications routed to manual review.
*   **System Reliability:** 0.00% "Fail-Open" audit exceptions (100% of decisions must be logged).

## 5. Functional Requirements
*   **FR1: Application Ingestion:** The system must accept a JSON payload containing standard applicant financial features and identity vectors (SSN/PAN).
*   **FR2: Identity Deduplication:** The system must securely hash identity vectors at the gateway to prevent duplicate applications within a 30-day window without storing plaintext PII.
*   **FR3: Deterministic Gating (E1, E2, E5):** The system must evaluate applicants against a version-controlled Rule Registry. Rejections must fail fast and halt further execution.
*   **FR4: ML Inference Profiling (E3, E4):** Approved applicants must be processed by the ML Inference Service to receive a Borrower Archetype label and a Credit Limit Recommendation.
*   **FR5: Dynamic Responses:** The API response must dynamically adjust based on the DAG flow. Rejected applicants receive explicit Adverse Action reasons. Approved applicants receive full profiles and improvement actions.
*   **FR6: Automated PDF Generation:** The system must generate an automated underwriting report PDF for bank employees.

## 6. Non-Functional Requirements
*   **NFR1 (Auditability):** Every state transition in the DAG must be written to an immutable PostgreSQL ledger via an asynchronous message broker.
*   **NFR2 (Fail-Closed):** If the audit ledger or rule registry is unreachable, the system must abort the transaction and fail closed. It must never issue an un-audited decision.
*   **NFR3 (Latency):** The end-to-end API response must execute in < 500ms (p95).
*   **NFR4 (Traceability):** Every API response must include a `lineage_metadata` block detailing the exact rule version and ML model UUID used for the assessment.

## 7. User Journeys

**Journey 1: The "Fail Fast" Rejection (Person B Flow)**
1. Applicant submits financial data via the frontend form.
2. The Orchestrator routes the payload to the E1 Eligibility Rules Engine.
3. The applicant's CIBIL score falls below the active threshold.
4. E1 returns a FAIL. The Orchestrator instantly halts the DAG (bypassing ML inference).
5. The applicant sees a rejection screen citing the specific credit score threshold and steps to improve it.
6. The exact rule version and rejection reason are committed to the immutable audit log.

**Journey 2: The Successful Approval (Person A Flow)**
1. Applicant submits financial data.
2. Orchestrator passes E1 and E2 Rules Engines successfully.
3. Orchestrator routes the payload to the ML Inference Service.
4. E3 K-Means Model assigns the "Mid-Career Established" archetype.
5. E4 Recommendation Model suggests a $15,000 credit limit.
6. Orchestrator verifies E5 Readiness (KYC rules).
7. Applicant receives a personalized success screen detailing their risk tier, archetype, approved limit, and actionable advice to maintain their tier.

## 8. System Boundaries
RiskIntel acts strictly as a decisioning and intelligence engine.
*   **Out of Scope:** Loan servicing, payment processing, fund disbursement, and core banking system ledger management.
*   **In Scope:** Application parsing, rule evaluation, ML profiling, limit recommendation, and compliance logging.

## 9. MVP Scope (V1.0)
*   Fully functional Orchestrator DAG.
*   Deterministic Rules Engine (E1, E2, E5).
*   ML Inference Service running the validated E3 Archetype model.
*   PostgreSQL Database with `assessments`, `results`, `audit_log`, and version registries.
*   REST API matching the frozen OpenAPI specifications.
*   A basic frontend UI allowing applicants to submit forms and view dynamic results.

## 10. Future Roadmap
*   **V1.1:** Implementation of the E4 Credit Recommendation ML model (currently relying on simple rules fallback in MVP).
*   **V2.0:** Open Banking API integration to ingest raw transactional data, migrating away from self-reported financial inputs to real-time cash flow features.
*   **V2.5:** Integration with external KYC/AML services to automate the currently deterministic E5 Readiness gate.
