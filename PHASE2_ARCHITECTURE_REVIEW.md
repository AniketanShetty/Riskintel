# Phase 2 Architecture & Sequence Review

## Current Plan Assessment

**Current Plan:**
* **Phase 2A:** trust_engine, resilience_engine, affordability_engine, coapplicant_engine
* **Phase 2B:** state machine orchestrator
* **Phase 2C:** verification processor
* **Phase 2D:** API layer

**Is this optimal?** **NO.** 

The current plan suffers from inverted dependency risks and delays integration testing of critical boundaries. 

1. **Delayed Verification (Phase 2C):** Building the Verification Processor *after* the Orchestrator and the Engines is dangerous. The Affordability Engine mathematically relies on the `verified_income` generated by the Verification Processor. The State Machine Orchestrator's most complex routing (`PENDING_REPROMPT`, `VERIFIED_WITH_VARIANCE`) depends entirely on Verification Processor flags.
2. **Big Bang Integration Risk:** By saving the API layer for Phase 2D, you cannot test a real end-to-end request (e.g., Intake -> State Mutated -> DB Persisted) until the very end of the project.
3. **Overloaded 2A:** Building the `coapplicant_engine` alongside basic affordability is premature, as co-applicant algebra is an advanced recovery state (`NEARLY_READY`) that requires the base orchestration to work first.

## Dependency Chains

To understand the optimal sequence, we must map the strict data and control flow dependencies:
1. **Data Dependency:** `affordability_engine` MUST consume data structured and approved by `verification_processor`.
2. **Control Dependency:** `state_machine_orchestrator` MUST consume output flags from `verification_processor` (to unlock optimization) and `affordability_engine` (to route to `READY` or `NEARLY_READY`).
3. **Recovery Dependency:** `coapplicant_engine` MUST consume the `emi_shortfall` output from the `affordability_engine`.
4. **Persistence Dependency:** The Orchestrator MUST map to the existing Phase 1 Persistence Layer schemas.

## Components for Independent Testing

The following components are stateless, functionally pure, and decoupled from the database. They can be unit-tested with mock payloads on Day 1:
1. **Verification Processor:** Pure cryptographic hashing (SHA-256) and boolean matching rules.
2. **Trust & Resilience Engines:** Pure variable threshold evaluation (Age, CIBIL, Vintage).
3. **Affordability Engine:** Pure mathematical PMT and arithmetic functions (assuming exact algebraic definitions are provided).

## Smallest Vertical Slice (The Core Spike)

The fastest way to de-risk the project is to build a vertical slice that connects Phase 1 (DB) to Phase 2 (Logic) using the simplest possible path:
**The Straight-Through Prime Borrower:**
* **API:** `POST /intake`
* **Orchestrator:** Handles `INTAKE` -> `TRIAGE` -> `PENDING_VERIFICATION` -> `VERIFIED` -> `READY`.
* **Engines Included:** Basic Trust, Basic Resilience, Basic Affordability.
* **Engines Excluded (Mocked/Skipped):** Verification Crypto, Optimization/Stretching, Co-Applicant Reverse Algebra, Reprompt Loops.

## Hidden Coupling Risks

1. **The `VERIFIED_WITH_VARIANCE` Trap:** If the Orchestrator (2B) is built without the Verification Processor (2C), the routing for variance downgrades might not map correctly to the Affordability engine's inputs.
2. **Identity Map Corruption:** Testing the Co-Applicant engine without the API and Orchestrator might hide SQLAlchemy Identity Map overwrites (a known risk from Phase 1). The Co-Applicant logic must be tested *through* the DB session to prove safety.
3. **State Machine Enums:** Building engines before the Orchestrator often results in the engines returning bespoke strings instead of the strict Orchestrator Enums, causing translation bugs.

## Alternative Implementation Orders

**Alternative A: The "API First" Approach (Mocked Engines)**
* *Order:* API Layer -> Orchestrator -> Verification -> Affordability -> Co-Applicant.
* *Pros:* Gets the frontend unblocked immediately. Proves DB persistence early.
* *Cons:* APIs will constantly change shapes as the underlying mathematical engines are discovered.

**Alternative B: The "Math First" Approach (Current Plan Tweaked)**
* *Order:* All Engines + Verification -> Orchestrator -> API.
* *Pros:* All business rules are mathematically proven before wiring.
* *Cons:* Big Bang integration. The Orchestrator might reject the structure of the mathematical outputs.

## Recommended Order

I recommend **The "Vertical Slicing" Approach**, weaving stateless math and orchestration together to prove integration continuously.

* **Phase 2A: Core Stateless Logic (Independent Testing)**
  * `verification_processor` (Hashing & Gate logic)
  * `trust_engine` & `resilience_engine`
  * `affordability_engine` (Base path only; no optimization)
  * *Why:* Proves the pure math works before touching the DB.
* **Phase 2B: The Primary Vertical Slice (Integration)**
  * `API layer` (Intake & standard Verification Webhook)
  * `state_machine_orchestrator` (Base states: `INTAKE` to `READY`/`HARD_REJECT`)
  * *Why:* Connects Phase 1 DB, 2A Logic, and APIs. Proves end-to-end integrity for the simplest applicant.
* **Phase 2C: Optimization & Cyclic Recovery (Advanced Math)**
  * `optimization_engine` (Tenure/Amount stretching)
  * `coapplicant_engine` (Reverse algebra)
  * *Why:* Isolates the highest-risk mathematical complexity.
* **Phase 2D: Advanced Orchestration (Complex Hooks)**
  * `state_machine_orchestrator` (`NEARLY_READY` recovery loops, `PENDING_REPROMPT` locks)
  * `API layer` (`/counter_offer_response`, `/reprompt_submission`)
  * *Why:* Attaches the complex recovery hooks to an already stable, functioning core system.
